# 예매 진입 플로우 동시 사용자 수용 한계 테스트

이 테스트는 로그인 성능이나 동일 좌석 경쟁이 아니라, 서버가 예매 진입 플로우를 반복 수행하는 **동시 활성 사용자 수를 어디까지 안정적으로 수용하는지** 측정한다.

```text
setup: 로그인 1회 → access token 준비 (측정 제외)

측정: 콘서트 상세 → 구역 조회 → 좌석 조회 → 좌석 선점 → 선점 해제
```

구역 조회는 좌석 조회에 필요한 `sectionId`를 얻기 위한 필수 중간 단계다. 선점 해제는 테스트 종료 뒤 좌석이 5분간 묶여 처리량이 왜곡되는 일을 막기 위한 정리 단계다.

## 사전 조건

1. **전용 부하 테스트 RDS**만 사용한다. 초기화 SQL은 기존 테이블을 지우고 테스트 데이터를 다시 만든다.
2. `loadtest0001`부터 `loadtest1000`까지의 계정이 로그인되어야 한다. 비밀번호는 모두 `password`다.
3. 테스트 시작 전 좌석이 선점되지 않은 초기 상태여야 한다. 중간 강제 종료가 있었다면 DB를 다시 초기화한다.
4. Grafana와 CloudWatch에서 HTTP p95/p99·5xx·JVM·DB connection·RDS CPU/IO를 함께 관찰한다.
5. 기본 최대 동시 사용자 수는 1,000명이고, 로그인 가능한 테스트 계정 수도 최소 1,000개여야 한다. VU 하나는 계정 하나만 사용한다.

## 실행

```powershell
$env:BASE_URL = 'https://<실제-API-도메인>'
$env:CONCERT_ID = '1'
$env:MAX_CONCURRENT_USERS = '1000'
k6 run .\seat-ramp.js
```

`SECTION_ID`를 지정하지 않으면 구역 조회 결과에서 잔여 좌석이 있는 첫 구역을 선택한다. 특정 구역만 비교하려면 지정한다.

```powershell
$env:SECTION_ID = '1'
k6 run .\seat-ramp.js
```

## 부하 곡선과 결과 해석

기본값은 동시 활성 사용자를 100 → 200 → 300 → 500 → 750 → 1,000명으로 올리고, 각 단계에서 5분간 유지한다. 각 VU는 동일한 순차 플로우를 반복한다.

| 단계 | 동시 활성 사용자 | 유지 시간 | 기록할 핵심 결과 |
| --- | ---: | ---: | --- |
| 1단계 | 0 → 100명 | 1분 | 워밍업 |
| 2단계 | 100명 | 5분 | 첫 안정 구간 |
| 3단계 | 100 → 200명 | 1분 | 다음 단계 진입 |
| 4단계 | 200명 | 5분 | 처리량·p95 변화 |
| 5단계 | 200 → 300명 | 1분 | 다음 단계 진입 |
| 6단계 | 300명 | 5분 | 안정 구간 확인 |
| 7단계 | 300 → 500명 | 1분 | 다음 단계 진입 |
| 8단계 | 500명 | 5분 | 최대 안정 구간 탐색 |
| 9단계 | 500 → 750명 | 1분 | 한계 구간 진입 |
| 10단계 | 750명 | 5분 | 한계 또는 안정 처리량 확인 |
| 11단계 | 750 → 1,000명 | 1분 | 최종 단계 진입 |
| 12단계 | 1,000명 | 5분 | 기본 테스트 상한 확인 |
| 종료 | 1,000 → 0명 | 2분 | 자원 회복 여부 |

전체 실행 시간은 종료 여유시간까지 약 38분 30초다. 실행 시간이 부담되면 `MAX_CONCURRENT_USERS=500`으로 먼저 수행한다. 그때 구간은 50 → 100 → 150 → 250 → 375 → 500명으로 비례 조정된다.

`setup()`은 `MAX_CONCURRENT_USERS`만큼의 계정을 작은 묶음으로 로그인하므로 최대 5분까지 허용된다. 이 시간은 동시 사용자 부하 측정 구간에 포함되지 않는다.

성공 판단은 다음과 같다.

- `booking_entry_flow_completed`: 성공한 전체 플로우 수와 평균 완료량
- `booking_entry_flow_completion`: 전체 플로우 성공률, 기준 99% 초과
- `booking_entry_flow_duration`: 콘서트 조회부터 선점 해제까지 걸린 시간, p95 3초 미만
- `seat_hold_duration`: 핵심 쓰기 API의 p95, 기본 기준 1.5초 미만
- `server_error_rate`: 테스트 플로우에서 받은 5xx 비율, 기준 0.1% 미만
- Grafana/CloudWatch: EC2 CPU·메모리, RDS CPU·connection·IO가 포화되지 않는지 확인

어느 5분 유지 단계에서든 위 기준 하나라도 깨지면, 그 단계는 실패다. 직전 통과 단계를 현재 구성의 **최대 안정 동시 활성 사용자 수**로 기록한다.

코드·인프라 변경 후에는 반드시 같은 공연, 같은 데이터 초기 상태, 같은 부하 곡선으로 재실행한다.

| --- | --- | ---: | ---: | ---: | ---: | ---: | --- |
| 1 | 100명 | 기록 | 기록 | 기록 | 기록 | 기록 | 통과/실패 |
| 2 | 200명 | 기록 | 기록 | 기록 | 기록 | 기록 | 통과/실패 |
| 3 | 300명 | 기록 | 기록 | 기록 | 기록 | 기록 | 통과/실패 |
| 4 | 500명 | 기록 | 기록 | 기록 | 기록 | 기록 | 통과/실패 |
| 5 | 750명 | 기록 | 기록 | 기록 | 기록 | 기록 | 통과/실패 |
