# 애플리케이션 메모리 조회수 전환 후 부하 테스트 결과

> 실행일: 2026-09-17
> 대상: `https://api.ticketmoa.site`
> 테스트 스크립트: `seat-ramp.js`
> 최대 동시 활성 사용자: 500 VU

## 목적

공연 상세 조회 시 DB의 `view_count`를 즉시 갱신하던 방식을 애플리케이션 메모리 카운터로 전환한 뒤,
기존 예매 진입 플로우에서 DB 행 락 경합과 연결 대기가 얼마나 줄었는지 확인한다.

테스트 플로우는 다음 순서다.

```text
공연 상세 조회 → 구역 조회 → 좌석 조회 → 좌석 선점 → 선점 해제
```

동일 공연 ID를 모든 VU가 반복 조회하므로, 이전 구현에서는 `concert.view_count` 단일 행에 대한
동시 UPDATE 경합이 발생했다. 이번 배포본은 해당 증가분을 애플리케이션 메모리에서 원자적으로 처리한다.

## 부하 구성

`MAX_CONCURRENT_USERS=500`으로 실행했다. 각 단계는 1분 ramp-up과 5분 유지로 구성된다.

```text
50 → 100 → 150 → 250 → 375 → 500 VU
```

공정한 비교를 위해 기존 실행과 같은 `seat-ramp.js`, 공연 ID, 계정 구성 및 테스트 환경을 사용해야 한다.

## 관찰

- 이전 실행의 오류 시작 시점은 약 22분으로, 250 VU 유지 구간이었다.
- 이번 실행의 첫 request timeout은 약 1,461초(24분 21초)로, 375 VU로 올리는 구간이다.
- 따라서 250 VU 구간의 안정성은 개선됐을 가능성이 높고, 장애 시작 구간도 뒤로 밀렸다.
- 이번 실행에서 공연 상세 조회 실패는 33,647건이다. 전체 HTTP 실패 33,851건의 대부분을 차지한다.
- 다만 상세 조회 실패 시 플로우가 즉시 종료되므로, 이 수치만으로 상세 조회가 유일한 병목이라고
  단정할 수는 없다. 같은 시점에 구역 조회, 좌석 조회, 선점, 해제에서도 request timeout이 발생했다.
- 전체 HTTP p95가 약 10초인 것은 timeout 요청이 지연 시간 분포를 지배하고 있음을 뜻한다.

## 추가 관측: DB 커넥션 풀 포화

Grafana와 Jaeger를 같은 부하 구간에서 확인한 결과, 현재 가장 직접적인 병목은 RDS CPU 포화가 아니라
백엔드의 HikariCP 커넥션 풀 대기다.

| 관측값 | 확인 내용 | 해석 |
| --- | --- | --- |
| HikariCP `pending` | 약 30에서 약 190까지 지속 증가 | DB 커넥션을 얻지 못한 애플리케이션 요청이 누적됨 |
| HikariCP `max` | 설정된 상한에서 유지 | 새 요청이 사용할 수 있는 커넥션을 더 만들 수 없음 |
| 요청 p95 | 약 0.3초에서 3초 이상으로 상승 | 커넥션 대기열 증가와 같은 시점에 지연이 확대됨 |
| Backend target | `DOWN` 전환 | 대기 누적으로 인한 헬스체크 실패·재시작·자원 압박을 추가 확인해야 함 |
| RDS CPU | 장애 직전 약 55% 수준 | DB 연산 CPU가 먼저 포화된 정황은 약함 |

Jaeger의 같은 좌석 선점 API 두 건도 이 해석을 뒷받침한다.

| 요청 | 전체 시간 | `UPDATE seat_hold` | 해석 |
| --- | ---: | ---: | --- |
| 느린 요청 | 4.7초 | 24.0ms | SQL 실행 전 약 4.6초가 비어 있어 커넥션 획득 대기가 유력 |
| 정상 요청 | 40.4ms | 23.8ms | 커넥션 획득 직후 SQL들이 순차 실행됨 |

따라서 좌석 선점 UPDATE의 행 락 대기가 4초 이상 걸린 것이 아니라, 커넥션을 받은 뒤의 SQL 실행은
두 경우 모두 수십 ms 수준이다. Jaeger만으로 대기 위치를 확정할 수는 없지만, SQL span 이전의 긴 공백과
HikariCP `pending` 급증이 동시에 나타나 커넥션 풀 획득 대기가 가장 유력하다.

## 결론

조회수 증가를 DB UPDATE에서 메모리 카운터로 옮긴 변경은 완료 처리량을 약 12% 높이고,
HTTP 실패율과 5xx 비율을 각각 1.38%p 낮췄다. 또한 오류 발생이 250 VU 유지 구간에서
375 VU 진입 구간으로 늦춰진 정황이 있다.

그러나 모든 통과 기준을 만족하지 못했고, 375 VU 이상에서 전 엔드포인트에 걸친 timeout과 5xx가
남아 있다. 따라서 조회수 UPDATE 락 경합은 완화됐지만, 현재는 HikariCP 커넥션 풀 포화와 그에 따른
대기열 누적이 가장 직접적인 병목이다. RDS CPU 포화는 현재 관측에서 주원인으로 보이지 않는다.

## 후속 확인

1. 부하 실행 시간대의 DB/트레이싱 로그에서 `update concert set view_count ...`가 실행되지 않았는지 확인한다.
2. HikariCP active/idle/pending/max, connection acquisition timeout 로그를 같은 시간축으로 비교한다.
3. 커넥션을 오래 점유한 URI와 트랜잭션을 찾아 좌석 선점·해제, 좌석 조회, 상세 조회별로 분리한다.
4. JVM heap·GC·OOM 이벤트, 컨테이너 재시작, ALB target health를 확인해 Backend target `DOWN` 원인을 확정한다.
5. 375 VU를 5분간 고정한 별도 실행으로 최대 안정 동시 활성 사용자 수를 확정한다.
6. 상세 조회만 반복하는 독립 k6 시나리오를 추가해, 예매·좌석 쓰기 경로와 분리한 조회수 개선 효과를 측정한다.

## 설계 제약

현재 구현은 단일 Spring 인스턴스의 메모리에 증가분을 보관한다. 따라서 애플리케이션 재시작 시
증가분이 사라지고, 여러 인스턴스가 배포되면 인스턴스마다 카운터가 분리된다. `ViewCountStore`
인터페이스를 유지한 채 Redis 구현체로 교체하면 이 제약을 해소할 수 있다.
