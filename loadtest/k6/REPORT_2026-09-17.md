# 예매 진입 플로우 동시 사용자 부하 테스트 결과

> 실행일: 2026-09-17
>
> 대상: `https://api.ticketmoa.site`
> 테스트 스크립트: `seat-ramp.js`

## 목적

로그인을 제외한 예매 진입 플로우를 반복하는 동시 활성 사용자를 현재 인프라가 어디까지 안정적으로 수용하는지 측정한다.

```text
콘서트 상세 조회
→ 구역 조회
→ 좌석 조회
→ 좌석 선점
→ 선점 해제
```

테스트 계정은 `setup()`에서 로그인해 access token을 미리 준비했다. 로그인·BCrypt 검증 비용은 측정 구간에서 제외했다.

## 부하 구성

이번 실행은 `MAX_CONCURRENT_USERS=500`으로 수행했다. 동시 활성 사용자는 아래처럼 늘렸고, 각 유지 구간은 5분이다.

```text
50 → 100 → 150 → 250 → 375 → 500 VU
```

각 VU는 고유한 테스트 계정으로 위 플로우를 반복했고, 성공한 선점은 즉시 해제했다. 따라서 좌석 소진이 처리량을 왜곡하지 않도록 했다.

## Grafana·CloudWatch 관측

- 백엔드 request rate는 최고 약 360~380 req/s까지 올랐고 이후 하락했다.
- 백엔드 p95는 부하 증가에 따라 약 2초까지 상승했다.
- Grafana의 backend target이 `DOWN`으로 표시됐다. 이는 Prometheus가 애플리케이션의 metrics endpoint를 수집하지 못한 상태다.
- Hikari DB connection pool의 `max`는 약 10개인 반면 `pending`이 약 190개까지 증가했다. DB 연결 대기가 대규모로 누적된 상태다.
- EC2 CPU는 최대 약 80%였고, 메모리 사용률은 약 65%에서 90% 부근까지 상승했다.
- RDS CPU는 약 58% 수준에 머물렀다. DB CPU 포화보다 애플리케이션의 연결 대기 또는 트랜잭션 경합이 우선 병목으로 보인다.
- RDS freeable memory는 약 96~128MiB였다. 여유가 낮지만, 이 값만으로 DB 메모리 부족을 단정하지 않는다.

Grafana 5xx 패널의 피크는 약 0.33%로 k6의 8.04%와 차이가 있다. Grafana 패널은 최근 5분 rolling rate만 보며, backend target이 DOWN 된 뒤에는 새 애플리케이션 메트릭을 수집할 수 없다. 상태 코드·URI별 정확한 5xx 원인은 Prometheus Explore와 애플리케이션 로그로 추가 확인이 필요하다.

## 병목 분석

이번 실패의 주 병목은 좌석 선점이 아니라 콘서트 상세 조회다.

`GET /api/v1/concerts/{concertId}`는 조회 때마다 `view_count`를 증가시킨다. 부하 테스트가 동일한 공연 ID를 반복 조회하면서 단일 `concert` 행에 대한 UPDATE 경합을 만들었다.

```text
동일 공연 상세 조회 동시 증가
→ view_count UPDATE 경합
→ 트랜잭션 완료 지연
→ DB connection pool 점유와 pending 증가
→ timeout·5xx
→ 좌석 조회·선점·해제까지 연쇄 지연
```

관련 구현:

- `ConcertServiceImpl.find()`는 상세 조회 시 조회수를 증가시킨다.
- `ConcertRepository.increaseViewCount()`는 DB에서 `view_count = view_count + 1`을 수행한다.

## 결론

500명 동시 활성 사용자 조건은 통과하지 못했다. 실패 로그는 약 22분 시점부터 시작됐고, 이 실행의 단계 구성상 250명 유지 구간에서 장애가 시작된 것으로 추정된다.

따라서 현 구성의 최대 안정 동시 활성 사용자 수는 **150명 이하**로 잠정 기록한다. 최종 수치는 150명과 200명 구간을 별도로 재실행해 확인한다.

## 다음 조치

1. backend target `DOWN`의 원인을 컨테이너 로그, EC2 메모리/OOM 이벤트, ALB target health에서 확인한다.
2. 상세 조회의 동기 `view_count` UPDATE를 Redis 누적 후 배치 반영 또는 비동기 이벤트로 분리한다.
3. DB connection pool의 크기만 즉시 늘리지 않는다. 단일 행 UPDATE 경합을 먼저 해소한 뒤 pool·인프라 사양을 조정한다.
4. 개선 후 150 → 200 → 250 → 300 VU를 각각 5분 유지하는 재시험으로 최대 안정 수용 인원을 확정한다.
